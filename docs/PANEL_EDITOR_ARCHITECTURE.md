# Архитектура редактора панелей умного дома

Актуальная точка входа для проекта «Умный дом». Срез на 20 ноября 2026 г.

## Текущий этап · 1.86.0 · 25 ноября 2026

База: опубликованный `v1.85.0` (`55692ad`). Пункты бэклога 11 и 12.
Этот раздел имеет приоритет над историческими контрактами ниже.

- YAML ссылки: `{element: lamp, w: 1.5, h: 1}`. У ссылки отдельный ID не нужен.
  Внутренний ключ — SHA-256 от JSON `[panel, section_index_or_null, element]`.
  Корневой список отличается от любой секции. Названия секций не участвуют в адресе.
- Индекс секции меняется при структурных операциях. API требует актуальный
  `draft_version` (конфликт — 409); UI сбрасывает выбор после структурных изменений,
  получения конфликтующей версии и восстановления вкладки с устаревшей версией.
  Эти ключи не предназначены для внешних постоянных ссылок.
- Явные ID старых ссылок читаются до миграции. Дубли таких ссылок в контейнере
  миграция отклоняет с номером списка/плитки, без раскрытия секретных значений.
  Новое добавление дублей запрещено. Одинаковый элемент в разных секциях разрешён.
- Inline schema 3 сохраняет собственный ID; копия inline получает новый ID.
  Копии ссылок в обеих схемах отдельный ID не получают. `from` остаётся read-only.
- `migrate` для legacy создаёт библиотеку без локальных размеров, записывая
  имеющиеся w/h в размещения. Для schema 2/3 снимает ID ссылок и фиксирует
  унаследованные библиотечные размеры в каждом размещении, не меняя defaults
  библиотеки и локальные overrides. Отсутствие размера сохраняется: не подменяем
  контракт типа константой 1×1. Добавление и копирование фиксируют имеющиеся defaults.
- Изменяемые include-ветви миграции копируются в `editor-placement-NNN.yaml`;
  неизменяемые ссылки и теги сохраняются. Исходные файлы остаются для отката.
  Локальные !secret между разными каталогами не переносятся молча: операция
  отклоняется. Повторный запуск не создаёт файлов.
- Публикация миграции использует RevisionStore, проверяет равенство разрешённой
  конфигурации, каналов и ESP JSON. Предпросмотр не пишет рабочие YAML; откат
  восстанавливает исходные байты. Тест: `tests/editor_placements_check.py`.

## Предыдущий этап · 1.85.0 · 21 ноября 2026

База — опубликованный `v1.84.1`, коммит `0e9941960743`. Подготовлена поставка

### Выполнено

- Для `switch` форма отделяет локальные `w/h/title` от `channel/command_topic`.
  Ссылка `element` редактирует общее определение; inline schema 3 редактирует
  только выбранную плитку. Метаинформация полей находится в зарегистрированном
  классе Switch (`editor_bindings`), независимого каталога нет.
- `update_binding` адресуется панелью, секцией и стабильным ID, проверяет
  принадлежность размещения и версию черновика. Запись идёт через AST, provenance,
  проверку ожидаемого дерева и прежний механизм публикации/отката.
- Форма показывает потребителей элемента. Diff возвращает `affected_panels`;
  учитываются прямая зависимость, транзитивные `from` и ссылки заставок.
  Подтверждение публикации повторяет проверку и список панелей, в том числе
  после восстановления ранее проверенного черновика. Список консервативный:
  учитывает операции и зависимости исходной и конечной конфигурации.
- `copy_panel`: поля `panel`, `section: null`, `new_panel`, `title`.
  `copy_section`: поля `panel`, `section`, `title`; копия вставляется сразу
  после исходной секции. У обеих операций обязательны `op` и `draft_version`
  в прежнем HTTP-конверте. Ссылки на библиотеку сохраняются, ID размещений
  генерируются заново. Inline-плитки копируются как независимые определения.
- Структурные include внутри копии разворачиваются, чтобы новая раскладка не
  меняла исходную. Ссылки scalar-значений, теги и `from` сохраняются.
  Назначения screens остаются прежними. Счётчики ID schema 3 обновляются.

### Границы и проверки

Привязки service/roles пока показаны только для чтения. Поиск MQTT-устройств
пока не добавлен. Пустое неизменённое защищённое поле сохраняет исходную ссылку;
новый введённый канал заменяет её обычным значением. Общие YAML alias/include,
которые меняют посторонние объекты, отклоняются. Копирование локального !secret
между каталогами отклоняется, чтобы не поменять источник секрета.

Приёмочный сценарий двух панелей проверяется в `tests/editor_library_check.py`:
локальное изменение, общее изменение, независимые копии, schema 2/3, include,
секреты, конфликты, команды, ESP JSON, публикация и побайтовый откат YAML.
`tests/editor_dom_check.js` исполняет JS редактора в jsdom с настоящим Flask API
без сетевого сервера. Это проверка поведения DOM, не визуальная проверка браузера.
Запуск Chromium в среде разработки блокируется системным запретом socket().
Физические WB, ESP32, телефон и Cloud в этом этапе не проверялись.

## Передача в следующий чат · 21 ноября 2026

База изменений — тег `v1.84.0`, коммит `f11deeb0` проекта `suklimovich-creator/wb-svg-panel`. Подготовлена поставка 1.84.1. Перед началом следующей задачи проверить тег, HEAD, версию в `wbpanel/__init__.py` и установленную версию WB. Прошивка ESP32 в эту поставку не входит.

**Что изменилось в 1.84.1.** При добавлении первого раздела к панели с корневыми плитками явный пустой список `sections: []` допускает тот же перенос, что и отсутствие списка. Перемещается исходный YAML-узел плиток, включая ссылку на файл. Если пустой список разделов сам подключён из внешнего файла, перенос корневых плиток требует отдельной операции с двумя источниками и редактор сообщает об ограничении.

После обновления вкладки редактор запрашивает модель прежнего черновика. Идентификатор и выбор панели, раздела и плитки хранятся в sessionStorage для пути редактора. Сервер остаётся источником подтверждённых правок. При временной ошибке можно повторить открытие, при утрате черновика — создать новый явно. Несохранённый ввод формы и черновики после перезапуска демона не восстанавливаются.

### Где работает кэш плиток

| Путь | Как обновляется |
|---|---|
| Рабочая веб-панель, сервер | В `wbpanel/web_live.py` функции `panel_watch` и `panel_version` отслеживают каналы панели. `cached_panel` возвращает готовый SVG варианта панели. При необходимости нового изображения вызывает `render_panel` для всей панели. Периодическое обновление по настройке HTTP (по умолчанию 10 секунд) обслуживает часы, графики и другие зависящие от времени элементы. |
| Рабочая веб-панель, браузер | `static/js/update.js` хранит последние представления SVG и сравнивает части изображения. При совместимой разметке обновляет изменившиеся части DOM. Перестройка структуры может потребовать полной замены. |
| Редактор, сохранение свойства | Успешная компактная операция обновляет модель и список. Выбор плитки или смена её размера сами по себе не требуют повторного запроса полного SVG. |
| Редактор, графический предпросмотр | `wbpanel/web_editor.py` передаёт рендереру подготовленную конфигурацию черновика в памяти. Явное обновление загружает цельный SVG. Общий кэш опубликованной панели для этого запроса непригоден, поскольку у черновика собственная версия и подготовка данных для показа. |

Отдельный серверный кэш фрагментов плиток остаётся пунктом `docs/ROADMAP.md`. Если замеры потребуют его реализации, начать с одного типа плитки. Проверить равенство SVG обычному рендеру при разных темах, размерах, позициях и значениях, затем проверить зависящие от времени элементы. Эти выводы относятся к веб-панели и редактору. Отрисовка в прошивке ESP32 требует отдельного разбора.

### Что проверить на контроллере

В инструментах браузера открыть Network, включить сохранение журнала. На одной панели записать по три замера для создания черновика, изменения ширины, ручного SVG, проверки diff и публикации. Для каждой операции сохранить HTTP-статус, Duration и заголовок ответа `Server-Timing: editor;dur=…` в миллисекундах. Для повторных публикаций нужны отдельные изменённые и проверенные черновики. Сравнить локальный адрес и Cloud. Duration включает транспорт и ожидание, заголовок измеряет обработку внутри приложения. У запроса, прерванного до получения заголовков, серверное время неизвестно. После тайм-аута проверить результат публикации через историю. На телефоне проверить сохранение прокрутки, на ESP32 — фактическое применение назначения после публикации.

### Что закрыть перед расширением редактора

1. **Первый раздел при пустом списке.** В 1.84.0 перенос корневых плиток выполняется при отсутствии sections. Если YAML содержит одновременно tiles и явное sections: [], интерфейс предлагает перенос, но сервер лишь добавляет раздел. Плитки остаются в корне, и рабочая панель начинает показывать разделы. Уравнять поведение двух форм YAML, проверить порядок, стабильность ID, !include и откат.
2. **Возобновление черновика.** Первая поставка может использовать уже существующий GET черновика. Хранить в текущей вкладке идентификатор черновика и выбор панели/раздела/плитки. При перезагрузке восстановить подтверждённые сервером правки. При истечении срока, перезапуске демона или смене базовой ревизии явно объяснить результат. Для восстановления после перезапуска демона потребуется отдельное решение о хранении на диске.
3. **Измерения на устройстве.** На одной реальной конфигурации измерить отдельно открытие, сохранение одного свойства, SVG и публикацию. Записать серверное время и время до ответа через Cloud. Проверить на телефоне возврат к выбранной плитке и получение новой раскладки физической ESP32. Предыдущий синтетический замер характеризует сохранение; задержку публикации в 25 секунд он не объясняет.

### Следующая функциональная задача

Начать этап 3 с одной плитки switch и двух панелей, использующих один элемент. Развести в форме изменение экземпляра (например, ширины на выбранной панели) и общей привязки (например, канала реле). После этого те же описания полей в реестре можно использовать для других типов и для поиска устройств.

## 1. Назначение документа

Документ фиксирует сквозную архитектуру редактора, чтобы каждая следующая задача развивала одну систему, а не предлагала заново собственный формат конфигурации, редактор или механизм публикации.

При реализации нового этапа сначала читаются этот документ, актуальный `docs/ROADMAP.md` и текущий код. Исследование аналогов повторяется только при появлении нового требования, которое здесь не рассмотрено.

Изменение архитектурного решения допускается, но сначала явно обновляется этот документ с причиной изменения. Нельзя незаметно реализовать альтернативную архитектуру внутри отдельного этапа.

### Контракт серверного этапа 1.80.0

- `elements` и `panels` — словари. Ключ элемента служит его ID,
  `id` экземпляра уникален во всей конфигурации. Тип при отсутствии
  `type` разрешается по существующим правилам реестра.
- Экземпляр задаёт `id`, `element` и при необходимости `w`, `h`,
  `title`. `Config.origins` индексирует источники элементов и
  экземпляров, `Config.tile_origin(id, *field_path)` возвращает
  физический файл, путь в нём и путь в развёрнутом дереве для поля.
- Мигратор создаёт отдельный элемент для каждой исходной плитки.
  Вложенные структурные include получают преобразованные файлы в тех же
  каталогах. Ссылки значений и теги секретов сохраняются. При конфликте
  с именем выходного файла миграция останавливается.
- Локальный интерфейс — `python3 -m wbpanel.editor_cli`. Python API —
  `RevisionStore`, `Draft`, `Changeset` и `Revision`. Черновик в памяти,
  сводка diff содержит счётчики файлов и объектов. История и журнал
  хранятся под `data/editor/`, снимки содержат исходные байты и
  доступны только владельцу каталога. Контрольные суммы защищены
  локальным ключом. Публикация принимает относительные include в
  пределах дерева конфига и отклоняет символьные ссылки. После
  аварийного завершения запись восстанавливается при следующем
  обращении к хранилищу, например командой `history`.
- Проверка публикации выполняется локально без MQTT и без запроса к
  экрану. Сравниваются разрешённые данные, каналы и ESP JSON.
  Редакторских HTTP-маршрутов и интерфейса в этой версии нет.

### Контракт структурного этапа 1.81.0

Поля экземпляра и схема 1.80.0 сохранены. Прикладные операции
`add_instance`, `remove_instance`, `move_instance` и `update_instance`
адресуют панель и раздел, а для существующей плитки ещё и стабильный ID.
Номер раздела относится к текущему черновику. Любой запрос изменения
проверяет `draft_version`, а сервис снова находит ID и проверяет его
принадлежность списку. `from:` и разделы без собственного списка
доступны только для чтения.

Сервер использует `Documents.nodes`, `Origin` и AST соответствующего
физического документа. Выходной YAML сериализуется из AST с сохранением
тегов и scalar-значений ссылок. После операции повторная загрузка
сверяет разрешённое дерево с ожидаемым. Если alias, merge или общий
include затрагивает другие объекты, операция отклоняется. Сериализуются
файлы с изменениями. При возврате AST к исходному состоянию сохраняются
исходные байты.

`GET /editor` открывает редактор, `GET /editor/<имя>` выбирает панель.
Маршруты API относительно `/api/editor` приведены ниже.

| Метод и путь | Запрос и результат |
|---|---|
| GET `/state` | Признак управляемой схемы. |
| POST `/drafts` | Тело `{}`. Создаёт черновик от текущей ревизии. |
| GET `/drafts/<draft_id>` | Панели, секции, экземпляры и безопасные записи библиотеки. |
| POST `/drafts/<draft_id>/operation` | `draft_version` и `operation`. Возвращает актуальную модель. |
| GET `/drafts/<draft_id>/diff` | Серверная проверка и сводка изменений без значений YAML. |
| GET `/drafts/<draft_id>/preview/<имя>.svg` | SVG кандидата. Параметры `draft_version`, `theme`, `cols`; `root_tiles=1` показывает корневой список отдельно, если панель настроена на отображение секций. |
| GET `/drafts/<draft_id>/tile/<имя>/<id>.svg` | SVG пульта зарегистрированного типа из кандидата. Поддерживает `draft_version` и `theme`. |
| POST `/drafts/<draft_id>/publish` | `draft_version`. Публикует проверенную версию и закрывает черновик. |
| GET `/revisions` | ID текущей ревизии и метаданные истории. |
| POST `/rollback` | `revision`, `base_revision`, `confirm: true`. Возвращает новую ревизию. |

У операции обязательны `op`, `panel` и `section` (число или `null`
для списка панели). Добавление принимает `element`, удаление принимает
`id`. Для перемещения нужны `id` и `direction` (`up` или `down`).
Для изменения передаются `id` и объект `fields` с нужными полями из
`w`, `h`, `title`. Размеры задаются числами от 0,5 до 32 с шагом 0,5.
`null` снимает переопределение размера, пустой `title` снимает
переопределение названия.

Каждый черновик получает непрозрачный ID и начинается с версии 0.
Операции одного черновика последовательны. Устаревшая версия получает
409 с текущей безопасной моделью. Изменение активного include или
secrets, публикация и откат меняют допустимую базу текущих черновиков.
Автоматического переноса правок нет. Проверка diff действует на
конкретную версию. Публикацию пустого changeset сервер отклоняет.
Неиспользуемые черновики удаляются через час. Активная конфигурация и
история переживают перезапуск процесса. Черновики хранятся в памяти.

Изменяющие HTTP-запросы требуют JSON до 8 КиБ и `X-WB-Editor: 1`.
Браузерный признак `Sec-Fetch-Site: same-origin` учитывает внешний адрес при проксировании через Wiren Board Cloud. Без этого заголовка переданный `Origin` сверяется с адресом запроса. Запрос из другого сайта или поддомена отклоняется.
Чтение истории и кандидата использует разделяемую блокировку без
восстановления журнала. Когда нужна аварийная сверка, её выполняет
операция с эксклюзивной блокировкой или локальная команда `history`.
Публикация и откат используют существующий журнал RevisionStore.
HTTP-откат работает между управляемыми ревизиями. `legacy-0`
остаётся доступен для восстановления через CLI.

Предпросмотр передаёт изолированный `Config` в существующую сборку
через параметры. Ни `web.config`, ни `assemble.config` не подменяются.
Снимки состояния MQTT и история используются для чтения. Названия с
секретами маскируются до подгонки текста, а ответы проверяются также
после декодирования HTML, JSON и URL-экранирования. При обнаружении
секрета в сформированном ответе SVG или JSON выдаётся безопасная ошибка.
Диагностика, которая может содержать поля конфигурации, подавляется
только в запросах редактора. SVG показывается пассивной картинкой и имеет `Cache-Control: no-store`.

Для HTTP-публикации изменён systemd unit: замена YAML через rename
требует записи в каталог основного конфига и его include. Код,
шаблоны, статика и файлы развёртывания явно монтируются read-only.

Исходная концепция требует уточнений для последующих этапов.

- Уже поддерживаются schema 2 с библиотекой и schema 3 с inline-плитками и счётчиками ID. Перед редактором библиотеки нужно согласовать, какой режим пользователь выбирает для новых устройств и как создаётся общая привязка.
- Этап 2 завершать по мобильным сценариям, сохранению фокуса и прокрутки, потере ответа и замерам на контроллере. Следом добавить восстановление черновика после перезагрузки страницы.
- Затем развивать декларативные метаданные REGISTRY и редактор библиотеки. Discovery использует эти же поля и выдаёт объяснимые предложения.
- Проверка текущего ESP JSON уже существует. Точный preview LVGL и проверка версии прошивки остаются этапом 4, их готовность требует проверки esp32-panel.
- Drag-and-drop и resize добавлять после устойчивого сенсорного выбора и свойств. Использовать существующие операции, отдельно определить поведение закреплённых x/y.
- Для секретов требуется отслеживание происхождения защищённых полей. Поиск совпадений строк по всем данным остаётся техническим долгом и может давать ложные срабатывания.

## 2. Основные решения

1. Основой интерфейса остаются готовые нативные плитки с собственной геометрией, анимациями, жестами и полноэкранными пультами.
2. `composite` является экспериментальным дополнением для простых и временных интерфейсов, а не заменой нативных плиток.
3. `wb-svg-panel` остаётся источником библиотеки, раскладки, цветов и конфигурации для SVG/PWA и ESP32.
4. Редактор один. SVG и ESP32 представлены отдельными рабочими областями предпросмотра с target-specific ограничениями, а не независимыми моделями.
5. Библиотека настроенных элементов общая. MQTT-топики, роли и мэппинги не копируются в каждую панель.
6. Редактор использует существующие реестр плиток, SVG-рендеринг и `/api/screen/<имя>`. Отдельный параллельный движок предпросмотра не создаётся.
7. Изменения публикуются через черновики, проверку, diff, историю и откат. Активный YAML не перезаписывается на каждое действие мыши.
8. Старый конфиг является источником для импорта и сохраняется в истории. После явной миграции рабочий конфиг переводится на новую структуру; бессрочная поддержка двух рабочих форматов не требуется.
9. Drag-and-drop появляется после стабильной модели идентификаторов, раскладки и безопасной записи.
10. Прошивка устройства, OTA и публикация в Git не входят в операции редактора конфигурации.

## 3. Термины и границы модели

### 3.1. Тип плитки

Реализация в коде: `switch`, `dimmer`, `curtain`, `thermostat`, `ac`, `clock`, `composite` и другие зарегистрированные типы.

Тип определяет:

- обязательные и необязательные роли;
- поля привязки и команды;
- зоны нажатий и жесты;
- компактное и полноэкранное поведение;
- допустимые размеры;
- поддержку SVG и ESP32.

Пользовательский редактор не создаёт новый нативный тип без реализации его рендеринга. Каталог типов строится из `wbpanel/registry.py`, а не дублируется вручную в отдельном JSON.

### 3.2. Элемент библиотеки

Настроенное устройство или логический элемент со стабильным идентификатором. Например, «Свет кухни» с типом `dimmer`, каналами включения и яркости, пределами и настройками пульта.

В библиотеке хранятся:

- тип;
- отображаемое название по умолчанию;
- MQTT- и service-привязки;
- диапазоны, шаги и единицы;
- мэппинги состояний, значков и цветов;
- настройки полноэкранного продолжения по умолчанию;
- разрешённые варианты представления.

### 3.3. Экземпляр на панели

Ссылка на элемент библиотеки и параметры конкретного размещения:

- стабильный `id` экземпляра;
- `element` — ссылка на библиотечный элемент;
- существующие `w/h`;
- порядок в списке;
- предусмотренные roadmap необязательные `x/y` для закреплённой позиции;
- ограниченный список разрешённых переопределений, например `title`.

Экземпляр не переопределяет MQTT-топики и команды. Если нужно другое устройство или другой мэппинг, создаётся отдельный элемент библиотеки либо явный вариант элемента.

### 3.4. Панель и физический экран

Панель — логический набор секций и плиток. Физический экран — конкретная ESP32 со своим адресом, прошивкой, состоянием связи и назначенной панелью. Эти сущности не смешиваются ни в конфигурации, ни в менеджере.

## 4. Структура конфигурации

### 4.1. Версии формата

Отсутствие явной версии обозначает исходный формат, который импортируется через адаптер. Управляемая конфигурация получает явную версию схемы, например `schema: 2`.

Номер схемы относится к структуре файлов и ссылок, а не к версии приложения. Миграции выполняются последовательно и проверяются на снимке до замены активных файлов.

### 4.2. Минимальное разбиение

```yaml
# config.yaml
schema: 2
elements: !include elements.yaml
panels: !include panels.yaml
```

```yaml
# elements.yaml
light_kitchen:
  type: dimmer
  title: Свет кухни
  channel: wb-mr6c_42/K1
  channel_dimmer: wb-mdm3_18/Channel 1
```

```yaml
# panels.yaml
main:
  title: Главная
  cols: 3
  tiles:
    - id: kitchen_light_main
      element: light_kitchen
      w: 2
      h: 2
```

Пример показывает целевую модель, а не требование немедленно изменить пользовательский конфиг.

На первом этапе достаточно `elements.yaml` и `panels.yaml`. Отдельный файл на панель вводится при реальном увеличении количества файлов, а не заранее:

```yaml
panels:
  main: !include panels/main.yaml
  bedroom: !include panels/bedroom.yaml
```

Существующие `!include`, `!secret` и `${имя}` продолжают обслуживаться `wbpanel/yamlx.py`. Секреты в библиотеку не копируются и в diff не выводятся.

### 4.3. Разрешение ссылок

Порядок получения полного описания плитки:

```text
контракт типа из REGISTRY
        ↓
элемент библиотеки
        ↓
разрешённые свойства экземпляра
        ↓
полное описание плитки для существующего конвейера
        ↓
registry / SVG / MQTT / /api/screen/<имя>
```

Разрешение выполняется до `Config.all_tiles()`, `used_channels()`, SVG-сборки и формирования ESP JSON. Эти компоненты не должны знать, была ли плитка записана старым inline-способом или ссылкой.

Произвольный рекурсивный merge переопределений не используется. Список свойств, которые экземпляр вправе менять, задаётся явно.

## 5. Миграция и обратная совместимость

### 5.1. Принцип

Обратная совместимость обеспечивается на границе импорта, при чтении до миграции и при откате. Она не означает обязательную вечную запись обоих форматов.

Редактор может прочитать исходный конфиг, показать его и подготовить миграцию. После подтверждения миграции активной становится новая структура, а исходные файлы остаются неизменным историческим снимком.

### 5.2. Сценарий миграции

1. Построить граф основного YAML и всех `!include`.
2. Сохранить исходные файлы как ревизию `legacy-0` до любых изменений.
3. Импортировать панели и inline-плитки во внутреннюю каноническую модель.
4. Найти повторяющиеся привязки и предложить элементы библиотеки. Не объединять автоматически элементы только потому, что у них совпал один топик.
5. Сформировать стабильные идентификаторы и показать конфликты или неоднозначности.
6. Подготовить управляемые `elements.yaml`, `panels.yaml` и изменённый корневой `config.yaml`.
7. Сравнить старую и новую конфигурацию после полного разрешения: панели, порядок, размеры, каналы, команды, ссылки и целевые ESP JSON.
8. Показать diff и результат проверки. Миграция выполняется только по явному подтверждению.
9. Опубликовать новую ревизию через общий транзакционный механизм.
10. После успешной проверки использовать только новую структуру. Откат восстанавливает сохранённые исходные файлы.

### 5.3. Комментарии и форматирование

Исходный файл в истории сохраняется байт в байт, включая комментарии и форматирование.

Если до миграции реализуется точечное редактирование исходного YAML, `yaml.safe_dump` для него не используется: комментарии должны сохраняться через round-trip редактор либо точечную правку. Это соответствует существующему `docs/ROADMAP.md`.

После миграции редактор вправе нормализовать управляемые файлы. Нормализация должна быть детерминированной, чтобы смысл и порядок не менялись, а diff не содержал случайного шума. Пользовательский исходник при этом остаётся доступен в истории.

## 6. Происхождение значений в include-файлах

Текущий `yamlx.py` возвращает объединённые данные и набор прочитанных файлов `touched`, но не сохраняет происхождение каждого значения. Для записи нужна карта:

```text
panels.main.tiles[kitchen_light_main].w
    → panels.yaml
    → panels.main.tiles[0].w

elements.light_kitchen.channel_dimmer
    → elements.yaml
    → light_kitchen.channel_dimmer
```

Загрузчик редактора должен различать:

- физический документ и его YAML-путь;
- логический путь после include;
- стабильный идентификатор объекта;
- значение до и после разрешения ссылок.

Индекс в списке не является долговременным идентификатором. После перестановки запись находит объект по `id`, а не по прежнему номеру.

## 7. Раскладка

Существующая поточная раскладка сохраняется. Порядок списка остаётся основным способом размещения, `w/h` задаются в существующих единицах сетки.

Дополнительные `x/y`, уже предусмотренные roadmap, вводятся только для явно закреплённых плиток:

- закреплённая плитка занимает указанное место;
- остальные размещаются существующим алгоритмом;
- перетаскивание обычной плитки меняет порядок, а не создаёт абсолютные координаты автоматически;
- коллизии и выход за сетку проверяются до публикации;
- размеры вычисляются от ширины экрана и `cols`, без фиксированных пикселей в конфигурации.

Drag-and-drop и resize являются другим способом изменить ту же каноническую модель, а не отдельным форматом раскладки.

## 8. Черновики, история и публикация

### 8.1. Сущности

- **Draft** — изменяемый черновик одной логической конфигурации.
- **Changeset** — набор изменений файлов и семантический diff черновика относительно базовой ревизии.
- **Revision** — неизменяемый опубликованный снимок всех управляемых документов и manifest.
- **base_revision** — ревизия, на которой основан черновик.
- **Rollback journal** — сведения, необходимые для восстановления файлов при ошибке публикации.

Предлагаемое хранилище внутри служебного каталога данных:

```text
data/editor/
  drafts/
  revisions/
    <revision>/
      manifest.json
      files/
  journals/
```

Это целевая структура, а не описание уже существующих файлов.

Manifest содержит идентификатор ревизии, время, родительскую ревизию, хеши файлов и краткое описание изменения. Секретные значения в manifest, diff и журнал не попадают. Локальные снимки защищаются не слабее исходного конфига и не отдаются публичным HTTP-маршрутом.

В версии 1.82.8 новый черновик получает базовую ревизию и разобранную конфигурацию за одно чтение дерева YAML. После каждой операции редактор хранит полученную модель и сводку изменений в памяти. При последующих запросах он сверяет ревизию и контрольные суммы файлов с базой. Это позволяет обнаружить внешнюю правку без повторного разбора тех же документов.

С версии 1.82.9 редактор применяет изменения к байтам YAML в памяти. При сохранении размера браузер отправляет поля выбранной плитки и получает номер версии черновика. SVG сохраняется на экране до явного обновления предпросмотра или смены панели.

### 8.2. Живой предпросмотр

Предпросмотр строится из черновика в памяти или изолированного временного дерева. Активный `Config` и рабочая ESP32 при этом не изменяются.

SVG-превью вызывает существующий конвейер сборки. Отдельный упрощённый редакторский рендерер не создаётся, иначе его расхождение с рабочей панелью станет постоянным источником ошибок.

### 8.3. Публикация

```text
черновик
  → проверка base_revision
  → повторное чтение активных файлов
  → формирование кандидата во временном дереве
  → полная загрузка и валидация кандидата
  → семантический и файловый diff
  → снимок текущей ревизии
  → запись изменённых файлов с rollback journal
  → перезагрузка и контрольная проверка
  → фиксация новой ревизии
  → уведомление заинтересованных экранов
```

Если активные файлы изменились после создания черновика, публикация останавливается с конфликтом. Пользователь видит изменения и выбирает повторное слияние; автоматически чужую правку нельзя затирать.

Групповая запись нескольких файлов не объявляется физически атомарной. Требуется транзакционный сценарий с временными файлами, атомарной заменой каждого файла и восстановлением уже заменённых файлов при сбое. Частично применённая ревизия не считается успешной.

После публикации повторно загруженная конфигурация должна соответствовать кандидату. При ошибке восстанавливается предыдущая ревизия, а активная панель остаётся рабочей.

После фиксации ревизии редактор закрывает исходный черновик и открывает следующий на выбранной панели. При потере ответа браузер запрашивает результат по ID отправленного черновика. Сервис хранит результаты последних 128 публикаций в памяти. После перезапуска сервиса результат можно сверить по истории ревизий и рабочей панели.

### 8.4. История

Удаление старой ревизии освобождает файлы её снимка. Служебная запись хранит связь с родительской ревизией, чтобы более ранние точки отката оставались доступны. Сервис завершает прерванное удаление под блокировкой при следующей операции записи. Активная ревизия защищена от удаления.

История хранит не только итоговый YAML, но и причину изменения, базовую ревизию и список затронутых документов. Поддерживаются:

- просмотр ревизии;
- сравнение ревизий;
- восстановление как нового черновика;
- явный откат через новую ревизию;
- экспорт резервной копии.

Откат не удаляет последующую историю.

## 9. Проверка конфигурации

До предпросмотра и публикации выполняются уровни проверки:

1. YAML, include-граф и отсутствие циклов.
2. Версия схемы и допустимые поля.
3. Уникальность и стабильность идентификаторов.
4. Существование ссылок `element` и отсутствие циклических зависимостей.
5. Обязательные роли из `REGISTRY`.
6. Совместимость каналов чтения и записи, включая MQTT `readonly`.
7. Размеры, закреплённые координаты и коллизии раскладки.
8. Поддержка возможностей целевой ESP32 и минимально необходимая версия прошивки.
9. Повторное построение каналов, команд, SVG и ESP JSON.
10. Отсутствие секретов в предназначенных для показа diff и preview-ответах.

Ошибка блокирует публикацию. Предупреждение показывается явно и не маскируется под успешную проверку.

## 10. Редактор библиотеки и MQTT discovery

### 10.1. Каталог типов

`wbpanel/registry.py` остаётся источником ролей, схем, полей, команд и зон. Для редактора в реестр постепенно добавляется только недостающая декларативная метаинформация:

- человекочитаемые названия и группы настроек;
- рекомендуемые и допустимые размеры;
- поддержка SVG/ESP32;
- возможности полноэкранного продолжения;
- ограничения версий прошивки.

Второй независимый каталог типов не создаётся.

### 10.2. MQTT-анализ

Существующий `tools/mqtt-to-config.py` является базой для повторно используемого read-only анализатора. Он использует `/devices/+/meta`, `/devices/+/controls/+/meta`, типы, диапазоны, единицы, `readonly`, `order`, названия устройств и каналов.

Подсказка должна быть объяснимой:

> Найдены переключатель и диапазон 0–100 в одном устройстве, поэтому подходит `dimmer`; оба канала доступны для записи.

Недостаточно показывать «популярный элемент» без причины. Discovery предлагает вариант и привязки, но не создаёт и не публикует конфигурацию автоматически.

Результат анализа кешируется как динамический инвентарь, а не записывается в YAML целиком. При отсутствии метаданных остаётся ручной выбор топика и типа.

## 11. Редактор панели

Первый UI — структурный:

- список панелей и секций;
- дерево плиток;
- добавление элемента из библиотеки;
- форма экземпляра;
- изменение порядка, `w/h` и разрешённых свойств;
- настройка полноэкранного продолжения в пределах контракта типа;
- живой SVG-предпросмотр;
- черновик, проверка, diff и публикация.

Следующий UI — drag-and-drop и resize в рамках той же сетки. Он вызывает те же операции модели, что и структурный редактор.

Редактирование сырого YAML может оставаться дополнительным режимом, но не является основой взаимодействия и не обходит проверки.

## 12. SVG и ESP32 preview

Используется один редактор с переключателем целевого представления:

```text
Общая модель и библиотека
  ├── SVG preview — существующий серверный рендеринг
  ├── ESP layout preview — быстрая интерактивная раскладка
  └── ESP native preview — снимок существующего симулятора LVGL
```

`esp32-panel/tools/sim/` является основой точного ESP preview. Он запускается изолированно с кандидатом JSON и возвращает изображение и диагностику. Неизвестные или неподдерживаемые возможности показываются явно.

SVG не называется точным ESP preview. Быстрый браузерный ESP preview также не заменяет проверку через симулятор перед публикацией целевых возможностей.

Preview на физической ESP32 является отдельным поздним этапом: временная ревизия, ограниченное время жизни, автоматический возврат и явное подтверждение. Оно не связано с OTA.

## 13. Редактор composite

`composite` — особый тип элемента общей библиотеки. Для него используется версионированный декларативный JSON без JavaScript и Lua на ESP32.

Внутри определения:

- MQTT-привязки объявляются один раз и получают локальные имена;
- примитивы ссылаются на локальные имена;
- состояния задают значки, цвета и доступность;
- компактная плитка и полноэкранный режим используют одни привязки;
- размер, вложенность и набор примитивов ограничены контрактом прошивки.

Редактор `composite` начинается после стабилизации библиотеки, черновиков и обычного редактора панели. Нативные плитки не переводятся на `composite`.

## 14. Менеджер панелей и экранов

Текущая главная `wbpanel/web_pages.py` развивается в менеджер, а не заменяется отдельным продуктом.

Для логических панелей показываются превью, состав, состояние черновика и опубликованная ревизия. Для физических экранов:

- online/offline и последний контакт;
- IP и версия прошивки;
- назначенная панель;
- ревизия или хеш загруженной конфигурации;
- поддерживаемые возможности;
- результат последнего получения конфигурации;
- доступные действия preview и администрирования.

Редактирование, временный preview и OTA — самостоятельные операции с разными разрешениями и подтверждениями. Управление парком и staged OTA не входят в MVP редактора.

## 15. Точки расширения существующего кода

- `wb-svg-panel/wbpanel/yamlx.py` — include-граф, происхождение узлов, чтение кандидата; существующие теги сохранить.
- `wb-svg-panel/wbpanel/config.py` — каноническая модель, разрешение ссылок до текущего конвейера, единая ревизия.
- `wb-svg-panel/wbpanel/registry.py` — контракты и недостающая метаинформация редактора.
- `wb-svg-panel/wbpanel/checkup.py` и связанные проверки — повторное использование валидации для черновиков и публикации.
- `wb-svg-panel/wbpanel/web_pages.py` — вход в редактор и менеджер панелей/экранов.
- `wb-svg-panel/wbpanel/web_screen.py` — проверка эквивалентности ESP JSON; не создавать второй target-конфиг.
- `wb-svg-panel/tools/mqtt-to-config.py` — выделение повторно используемого discovery без автоматической записи.
- `esp32-panel/tools/sim/` — точный native preview и проверка кандидатов.
- `wb-svg-panel/docs/ROADMAP.md` — связь с уже запланированными `id`, `x/y` и безопасной записью.

Новые модули для черновиков, миграций и истории выделяются по ответственности, а не добавляются целиком в `web_pages.py` или `config.py`.

## 16. Этапы и критерии перехода

### Этап 1. Модель, миграция и история

Результат: версионированная модель, `id`, ссылки библиотеки, include-provenance, снимок исходника, проверка эквивалентности, revisions и безопасный changeset.

Переход дальше возможен, когда старый конфиг можно импортировать, опубликовать в новой структуре и восстановить без потери панелей, каналов и команд.

### Этап 2. Структурный редактор панели

Результат: добавление элемента, порядок, `w/h`, разрешённые свойства, живой SVG preview, draft/diff/publish/rollback.

Переход дальше — после проверки конфликтов параллельного редактирования и ошибок записи.

### Этап 3. Редактор библиотеки и discovery

Результат: создание и изменение элементов, MQTT-подсказки с объяснением, проверка ролей и повторное использование элемента несколькими панелями.

### Этап 4. ESP32 workspace и базовый менеджер

Результат: target-specific проверки, симуляторный preview, список физических экранов, назначение панелей и отображение ревизий.

### Этап 5. Drag-and-drop и resize

Результат: операции мышью используют модель этапов 1–2; поддерживаются поточный порядок и явно закреплённые `x/y`.

### Этап 6. Редактор composite

Результат: версионированный декларативный формат, общие привязки, компактный и полноэкранный режимы, SVG/ESP preview и ограничения прошивки.

### Этап 7. Preview на устройстве и расширенный менеджер

Результат: временный preview с возвратом, наблюдение за парком и отдельно спроектированные административные операции.

## 17. Что не делать

- Не создавать два независимых редактора с разными схемами для SVG и ESP32.
- Не дублировать реестр плиток ручным каталогом свойств.
- Не копировать MQTT-привязки в экземпляры панелей.
- Не перезаписывать активный YAML при каждом движении мыши.
- Не использовать `yaml.safe_dump` для сохранения немигрированного пользовательского YAML с комментариями.
- Не объявлять запись нескольких файлов атомарной без rollback journal.
- Не подменять честный ESP preview приближённым SVG.
- Не превращать `composite` в универсальную замену нативных плиток.
- Не смешивать preview конфигурации и OTA.
- Не выполнять push, прошивку или OTA как побочное действие работы над редактором.

### Миграция из исходного YAML в 1.82.1

Публичная команда `editor_cli migrate` строит schema 2. Ключ элемента
сохраняет исходный ID или получает номер в пределах типа. Определение
хранит все заданные свойства. Первый экземпляр получает тот же ID и ссылку
на элемент. Дальнейшие экземпляры имеют собственные ID. Существующие
конфигурации schema 3 продолжают загружаться. Проверка модели редактора
охватывает значения из конфигурации отдельно от служебных ключей JSON.
SVG проходит проверку целиком после рендеринга.

### Ссылки панели в 1.82.2

В schema 2 запись `{element: switch-001}` обозначает размещение на панели.
Порядок задаёт список tiles. Поля w, h и title переопределяют свойства только
этого размещения. Для такой записи сервер адресует операции по паре
(панель, элемент), представленной стабильным внутренним ключом. Перестановка
и выбор секции не меняют ключ. Старые явные id сохраняются. Для второго
размещения того же элемента допускается явный id. Публикация и разрешение
YAML продолжают использовать Config.origins и RevisionStore.
